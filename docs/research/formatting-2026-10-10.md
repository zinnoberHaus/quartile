# Formatting and numerical notation research

Date: 2026-10-10. Baseline inspected: `d1213dedc24da22bcc5ae5a63cc16b2b38c9aa41`. This records evidence and the proposed upgrade, not a claim that every recommendation was already implemented at that baseline. See the [formatting guide](../guides/formatting.md) for the resulting public API.

## Primary-source evidence

| Source | Documented capability | Quartile judgment |
| --- | --- | --- |
| [ECMA-402](https://tc39.es/ecma402/#numberformat-objects), [NumberFormat options](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/NumberFormat) | Native locale-aware decimal, currency, percent, unit, compact, scientific and engineering formatting. Fraction digits and significant digits are different controls; rounding priority determines which applies. Rounding increments have additional constraints. | Keep `Intl` as the default display engine. Preserve explicit options; validate incompatible combinations before rendering JSON specs. Avoid a second competing currency/locale system. |
| [NumberFormat input and output](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/format) | Modern implementations format `bigint` and decimal strings without first rounding through a JavaScript Number. Older implementations differ. Output may include nonbreaking spaces and bidirectional controls. | Preserve exact display inputs and locale punctuation. Test supported runtimes; do not equate display support with exact aggregation, scale coordinates or JSON bigint serialization. |
| [DateTimeFormat options](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat/DateTimeFormat) | Locale, calendar, numbering system, hour cycle and time zone are independent controls. Date/time styles cannot be combined with individual date/time components. | Add provider and field time zones with explicit descriptor overrides. Set locale and zone in reproducible reports. Formatting an instant must not silently change aggregation or calendar-day selection semantics. |
| [FormatJS core](https://formatjs.github.io/docs/intl/), [React Intl imperative API](https://formatjs.github.io/docs/react-intl/api/) | Cached Intl wrappers, named formats, translated messages and date/number parts. The imperative API is recommended for string attributes and large collections of cells; reuse the intl instance, recreating it when locale/messages change. | Support application-owned formatter callbacks. Applications already using React Intl can reuse their instance; the chart library does not need to install a translation framework or a React component per tick. |
| [FormatJS NumberFormat polyfill](https://formatjs.github.io/docs/polyfills/intl-numberformat/) | Capability detection, conditional loading and locale data are explicit steps. | Keep polyfills an application choice. Native constructor success alone does not prove an older engine honors every newer rounding option; inspect capabilities when that behavior is required. |
| [math.js format](https://mathjs.org/docs/reference/functions/format.html) | Fixed, exponential, engineering and automatic notation; automatic exponent thresholds; fractions and numeric callbacks. `precision` means fractional places for fixed notation and significant digits for exponential/engineering/auto. | Document optional callbacks for specialist output. Do not map a single ambiguous “precision” setting to all notations. Do not use a mathematical expression parser to format untrusted dashboard specs. |
| [math.js BigNumbers](https://mathjs.org/docs/datatypes/bignumbers.html) | Configurable computation precision, 64 significant digits by default; conversion to Number loses precision, and finite precision still cannot represent all fractions exactly. | Compute with the appropriate backend/decimal type, then hand exact text or strings to the display boundary. Construct high-precision values from original strings rather than already-rounded Number values. |
| [math.js units](https://mathjs.org/docs/datatypes/units.html) | Dimensional units can be converted; `toNumber` returns Number, while `toNumeric` preserves the underlying numeric type. | Normalize measurement units upstream. An Intl unit label does not convert Celsius to Fahrenheit or seconds to milliseconds. Keep dimensional conversion separate from display scaling. |
| [d3-format](https://d3js.org/d3-format) | SI prefixes, trimming, significant/fractional precision and custom locale definitions. `formatPrefix` holds one prefix across a set; precision helpers derive useful decimal precision from a step. | Use these ideas for consistent axes and optional callbacks. SI prefixes differ from locale compact notation, and neither implies binary byte units. Tick precision should preserve distinct adjacent labels. |

The right boundary is **calculation → typed data → display**. Changing a label must not change sorting, filters, totals, selection identity or exported raw records. A pretty representation cannot repair floating-point arithmetic that has already lost information.

## Baseline capability and gaps

The existing [`data/format.ts`](../../packages/react/src/data/format.ts) already centralized named formats, number-option objects and string callbacks, cached Intl instances, and reused field formats in tables and charts. The audit found these concrete limitations:

- `compactNumber` used English K/M/B suffixes and a decimal point; compact currency manually prefixed a symbol, losing locale-specific order and spacing. Named currency also abbreviated automatically at 100,000 and forced a two-place maximum instead of respecting each currency's defaults.
- Default number formatting rounded to two fractional digits, hiding very small nonzero measurements. Axis `short` formatting had no separate field-level contract; an abbreviated axis and an exact tooltip were hard to describe together.
- `finiteNumber` converted strings through Number and rejected bigint. Plain text could preserve them, but numerical display could lose exact digits.
- Date names had no configurable zone. `month` combined a localized month with a manually generated Gregorian/local year. Delta formatting used `toFixed` with fixed English punctuation.
- Bare number options were accepted in React but the JSON schema allowed named formats only. Invalid Intl combinations could reach a constructor during rendering. Field explanations and chart methodology notes had no common tooltip path.

## Recommended contract

Preserve existing names, number-option objects and callbacks; add discriminated descriptors with `type: 'number' | 'date' | 'bytes' | 'duration'`. Number descriptors should expose Intl options plus explicit locale, missing text, prefix/suffix and display scale. Date descriptors should expose DateTimeFormat options. Bytes should distinguish base 1000 from 1024; elapsed duration should specify seconds versus milliseconds and remain separate from a clock timestamp.

Add `axisFormat`, `tooltipFormat`, `description` and `timeZone` to field metadata. A component override should take precedence over the applicable field format, then provider defaults. Automatic short-axis behavior should apply only when no explicit axis/number options dictate the representation. Full values belong in tooltips, tables and KPI values by default; abbreviations are an explicit product decision. Render explanatory text as text, never HTML.

Expose shared field/range formatters and structured parts so accessible labels, ranges and rich tooltips use the same contract. Keep currency position, localized signs and bidirectional literals intact. Cache constructed Intl formatters by effective locale/options; bound the cache for applications accepting many user configurations. Validate the serializable subset, unknown keys, finite bounds, time zones and constructor-level option conflicts before mounting a spec.

FormatJS, math.js and d3-format are optional adapters through callbacks, not new mandatory dependencies. Such functions belong in application code and cannot be serialized into dashboard JSON. Mathematical objects also require an explicit conversion boundary: no implicit promise of BigNumber-aware chart scales or aggregates.

## Verification priorities

Cover English, French, German, Indian grouping and Arabic digits; USD, JPY and KWD; accounting signs and rounded negative zero; null, empty input, NaN and infinity; tiny nonzero values and compact boundary rollover; precise strings/bigints; ratio-percent versus percentage-point changes; decimal/binary bytes; elapsed durations above 24 hours; and dates around UTC midnight and DST changes. Verify explicit fractional/significant precision and invalid combinations. Test actual tooltips, exact tables, KPIs, axis ticks and accessible summaries together, including keyboard interaction and SSR with an explicit locale/time zone.

These are product-specific recommendations inferred from the evidence above. Full translation of interface copy, arbitrary-precision chart arithmetic, automatic unit conversion and an expression language are outside this formatting upgrade.
